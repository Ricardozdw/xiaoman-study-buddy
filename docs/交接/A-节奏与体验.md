# 交接 · A 节奏与体验

> A 不写某一条的业务代码。各线负责人见 [地基给各线](../地基给各线.md)（2026-11-04 确认）。

> 先读 [分工方案](../分工方案.md)：产品规则、技术约定、协作方式对所有人都适用。

## 你负责什么

整个项目的节奏和最终体验：定开工和上线日期、盯进度、验收每条线交来的模块、设计并实现所有线共用的界面层、写小满的文案和表情、每天分诊 bad case，最后把所有模块合并到 main 并上线。

**共用界面层**包括：对话页整体（对话流、输入框、左栏、右侧工作台）的布局和交互；7 种卡片组件的样式和交互（怎么出现、原地更新、收成一行，加载 / 失败 / 空状态）；小满的形象、表情和 5 个露出时刻的动效；浅色和深色主题、可访问性、窄屏。各线用这些组件拼出自己的功能，卡片里放什么数据、点了按钮后发生什么，由各线负责。

## 要做出什么

- **一份排期**：开工日、各线交付日、合并（至少 1–2 天）、界面和交互优化（至少 2–3 天）、上线日，大家认可。
- **界面方向（开发期间做）**：找参考（同类产品和设计案例），定下视觉和交互方向，做出设计稿；想清楚交互上要改的地方。
- **共用界面层（功能版本跑通后做）**：在地基给的朴素组件基础上，实现最终的对话页、7 种卡片（目标拆解、进度、文档摘要、题目、建议、重排、收工）、左栏、工作台和小满的 5 个露出时刻（每天第一次打开、状态变化、收工和里程碑、空状态、拆解卡和建议卡）。因为各线只用公用组件和颜色变量，改这些地方会让所有线一起变。可能顺带调整一些小功能：动某条线的代码前先跟负责人说，改完跑自动测试、走一遍演示 8 步。小满形象参考旧原型里的卡皮巴拉设定（`manman-prototype/qa/_shots/character/`）。
- **小满的文案**：开场白、建议卡、收工、中断后回来三种情况的说法，交给计划线放进提示词。语气温和、不追责、不施压。
- **bad case 分诊**：每天看一遍新增的 bad case，按类型分给对应的线（问答 / 意图 → 问答线，出题 / 错题 → 练习线，学习文档 → 资料线，开场 / 建议 → 计划线），高严重度当天处理。
- **验收与合并**：每条线交来时，对照 PRD 的验收标准在浏览器里点一遍；全部合并后完整走一遍演示 8 步，问题当场分给对应的人修。
- **保底版本**：合并后演示 8 步跑通，先存一份“能上线的功能版本”（例如在 GitHub 打一个标签），界面优化出问题时可以直接用它上线。
- **上线**：界面和交互优化完成、演示 8 步再次全部跑通后上线；准备演示脚本和录屏备份。

## 做到什么算完成

- 上线后的网页能用一门公开课的真实 PDF 走完演示 8 步，不靠截图。
- 每条 PRD 验收标准都有人在浏览器里确认过。
- 界面上没有违反 8 条产品规则的地方，比如出现“连续 N 天”、责备的话，或者一次推两张卡。
- 各线的界面风格一致；满足 PRD 的可访问性和兼容要求（正文 ≥ 15px、可点区域 ≥ 44×44、浅色和深色主题、窄屏不横向滚动）。
- 上线时 bad case 库里没有未处理的高严重度问题。

## 你说了算的事

- 共用部分（对话页骨架、卡片组件、数据表、接口约定）要不要改、怎么改。
- 各线之间的边界和冲突。
- 什么时候砍范围。比如交付前某条线做不完，可以先砍图片和扫描件，学习文档只留要点和知识点。
