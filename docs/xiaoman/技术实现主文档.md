对照着读：**Dify 工作流 → 后端的“AI 能力”**（版本化提示词文件 `app/prompts/<名字>/vN.md` + 后端函数，经底座模型网关调用）；**Dify 模型供应商 → 底座模型网关**（FAST / STRONG 两档模型链，出错自动换备用，换模型改 .env）；**Dify 日志和 DSL 导出 → 底座的调用轨迹、用量记录，提示词文件进 Git**；Dify 云版的额度和套餐费不再有。架构图和路线图里的“Dify”字样还没重画，以文字为准。

## 一页总览

结论：用 **Personal-Agent 底座（FastAPI + LangGraph）+ React 前端 + Supabase 存储** 就能做出最小闭环。两周内**不用知识库**：后端把资料抽成带页码的文字，整讲交给模型（直接方案），以后再换成自己搭的知识库。AI 能力写成版本化的提示词文件，组员用 Claude Code / Codex 改提示词、跑评测，代码都让 AI 写。最大的风险是回答和出题的质量，评测从第 1 天开始。

产品闭环：上传资料 → 后端抽出带页码的文字 → 生成学习文档 → 提问（整讲全文交给模型，回答标页码）/ 出题 → 记录作答 → 更新掌握度 → 复习排进“今天三件事” → 数据看板。

（图：整体技术架构 · 前后端 + Dify——见在线文档）

前端只和后端说话；后端管账号、计划、做题记录这些业务数据，需要 AI 时经底座的模型网关调模型；用哪个模型改 .env 配置，不改代码。

小满（agent）不是一个单独的页面，而是挂在这条链上的“事件处理器”：每一步完成后被唤醒，判断是提醒、给建议卡，还是（用户授权后）直接做并留下可撤销记录。

本文默认的前提（如不对请在评论里改）：Web 端先行；项目周期 2 周；后端以 Personal-Agent 为底座；前端建议新建 React 项目，只复用慢慢原型的配色和小满形象（待确认）。

## 产品定位与核心价值

**一句话：你只管上课和交资料，小满记得你学到哪，每天告诉你该学的三件事，让你看得见自己在进步。**

### 和市面上的产品比

单看“上传资料 → 整理 → 问答 → 出题”，市面上已经有做得很好的产品。如果我们只做到这一步，就是一个更差的 NotebookLM。下表是截至 2026 年中的了解，组里开工前请再核实一遍。

| 产品 | 擅长 | 缺的 |
| --- | --- | --- |
| NotebookLM | 上传资料后问答带出处，生成学习指南、测验、闪卡 | 不管你哪天学、学到哪；每次打开都要自己想“今天干嘛” |
| ChatGPT / Kimi / 豆包 | 什么都能聊，有记忆，也有学习模式 | 不知道你的课程结构；记忆是零散的事实，没有学习进度 |
| Anki / Quizlet | 间隔复习，帮你记住卡片 | 卡片要自己做，也不懂你的资料 |
| 多邻国 | 每天推你学，习惯养成做得好 | 内容是它定的，不是你的课；靠连胜和愧疚感驱动 |

区别在于：别的产品围着“资料”转，慢慢围着“你”转。NotebookLM 记得你的资料，Anki 记得你的卡片，小满记得你：学到第几讲、哪里老错、哪里标了“模糊”、考试还有几天、每天大概有多少时间。

### 核心价值：三件别人没串起来的事

1. **连续性**：今天的安排来自昨天做错的题。“资料 → 做题 → 错题 → 复习 → 进步”是一条线，在别的产品里是断开的。
2. **主动性**：用户不用想“今天学什么”，打开时小满已经安排好了。载体就是“今天三件事”，这是 personal agent 和聊天机器人的区别。
3. **陪伴而不施压**：不搞连胜、不让人愧疚，只和自己的过去比。

### 由此定下的决定（2026-11-03）

- **交互形态：对话优先**（原型 v5）。中间是和小满的对话，交资料、看整理结果、提问、做题、排复习都从对话开始，结果以卡片形式出现；左栏只放“今天”和“我的资料”；学习文档全文、原文出处、完整看板在右侧工作台按需打开。原型在 manman-prototype/qa/_shots/prototype-v5-对话优先/。
- **“今天三件事”从大目标拆出来（方案 A 升级）**：第一次见面时问目标（考试日期）、课程一共几讲、每天有多少时间，小满出一张“目标拆解卡”（分阶段：学新讲 / 刷题 / 冲刺），点了才生效。每天三件各从一处来：**学新的**（按进度该学的那一讲）、**练一练**（给学过的讲出题）、**补一补**（错题和快忘的内容）；某处当天没东西，就由另外两处顶上。全部用后端规则算，不用 AI。两周内只做“自动排 + 打勾 + 换强度”，不做手动添加和改期。
- **强度分三档，不给单个任务分难度**：轻松（约 15 分钟）/ 正常（约 30 分钟，默认）/ 冲刺（约 50 分钟）。件数始终三件，变的是每件的分量：看要点还是看全文、练几道题、有没有难题。用户在左栏直接切换；小满想换档（用户说“今天只有 15 分钟”，或连续几天正确率很高）先出建议卡，点了才换，可撤销。题目本身的易 / 中 / 难作为出题工作流输出的一个字段，冲刺档才出难题。不给任务标“高难度”，避免给用户压力。
- **小满在 5 个时刻露出**：每天第一次打开（大形象打招呼）；状态跟着事情变（读资料在想、答对开心、答错安慰）；收工和里程碑（大一号的庆祝）；空状态（还没目标、今天都做完）；拆解卡和建议卡（小满“亲手”交给你）。做题时只留头像；不做常驻大形象、桌宠和成长收集。两周内用现有素材（旧原型的场景动画和像素小满）。
- **中断几天再回来**：不堆积、不追责。没做的任务不累加，回来那天仍最多三件；小满开场不提断了几天，建议当天换“轻松”（建议卡）；“补一补”优先挑最容易忘的（错题、隔得最久的讲），“学新的”接着上次没学完的讲。计划落后分三种：落后不多（在计划留的复习余量内）→ 建议卡说明“从复习时间里挪出来，考试计划不变”；落后较多 → 重排卡给 2–3 个选项（几天用“冲刺”档 / 压缩刷题周 / 部分讲只看要点），用户选；超过 7 天没来 → 先问目标还算不算数（照旧 / 考试日期变了 / 先休息一阵）。所有改动点了才生效、可撤销。回来时只出一张卡（强度和补课合并成一个安排），用户点完才带第一件任务；一次只让用户做一个决定。看板只显示“这周学了 N 天”，不做连续打卡。
- **做题在对话里怎么呈现**：一组题只用一张卡，原地换题；每题答完看解析，点“下一题”才换；做完收成一行总结（答对几道），可展开回看。做题时前面带答案的对话先收起。重做错题答错不卡住：看完解析继续下一题，这道放回“补一补”，过几天换个问法再出。任务按“做了”算完成，对错只影响掌握度。
- **学习记录就是记忆**：做题、错题、进度、自评把握度都要存下来，这是连续性和主动性的基础。只记学习数据，不做通用的聊天记忆。
- **两周内不用 Dify 知识库（直接方案）**：Dify 知识库的解析和切块效果不理想，先不用。后端把资料抽成带页码的文字，整讲交给模型；后端留一个“取资料内容”的替换口，以后换成自己搭的知识库，前端和提示词都不用改。
- **精力分配**：问答和出题做到能用就行，主要靠底座现成的模型网关和评测工具；省下的精力放在“学习记录 + 每天安排 + 看板”这条线上，重点是后端 D 和 AI 2（F）。

### 演示怎么讲：围绕“第二天”

最该打动人的不是“它能回答问题”（谁都能），而是第二天打开的那一刻：

> 小满：“早。昨天第 3 讲你在‘转移和减轻’上错了 2 道，今天先花 5 分钟重做这两道。”
>

演示脚本按两段排：

1. **第一天**：说出目标和考试日期 → 确认目标拆解卡，左栏出现今天三件 → 交一讲课件、看学习文档 → 问一个问题（回答带出处）→ 做 5 道题，错 2 道 → 复习上一讲术语 → 收工，小满告诉你明天的三件。
2. **第二天**：打开后小满先开口，三件事是“补一补：重做昨天的错题”“学新的：第 7 讲”“练一练：第 5 讲几道题”；说“今天只有 15 分钟”会出建议卡换成“轻松”→ 三件做完，看板上掌握度上升。

两周的里程碑按“第二天这一刻必须真实跑通”倒推：第 3–5 天跑通第一天，第 6–8 天跑通第二天，最后 2 天打磨和彩排。具体见下面“协作流程与里程碑”。

## 技术栈选型

原则：后端在开源底座上加功能，不从零写；AI 能力写成提示词文件、经底座模型网关调用；代码交给 AI 写；能用现成云服务的不自己部署。

| 层 | 选型 | 谁、用什么做 | 说明 |
| --- | --- | --- | --- |
| 前端 | React + TypeScript + Vite（建议新建，复用慢慢配色和小满形象，待确认） | B、C 用 Claude Code / Codex | 只调后端接口；不用底座自带的原生 JS 界面 |
| 图表 | ECharts | C 用 Claude Code / Codex | 看板的图表现成 |
| 后端底座 | [Personal-Agent](https://github.com/hubooooooo/Personal-Agent)（MIT，Python 3.12 + FastAPI + LangGraph） | D 在 VS Code 里用 Claude Code 或 Codex 插件 | 复用模型网关、用量记账、👍 / 👎 反馈、版本化提示词、回归测试、确认卡、登录和行级权限；我们新加的路由放单独模块；飞书 / 微信 / 抓取 / 写草稿 / 安全输入区关掉 |
| 存储与登录 | Supabase 的 Postgres（底座设 DATABASE_URL 切换）+ Supabase 文件存储；登录用底座的网页会话 | D | 不用 Supabase 登录；user_id 只从服务端会话推导 |

| AI 能力 | 版本化提示词文件 `app/prompts/<名字>/vN.md` + 后端函数 | E、F 写提示词，D 写函数 | 改提示词新建下一版，哈希被测试锁定 |
| 模型 | 底座模型网关配一主一备（FAST / STRONG 两档模型链，出错、超时、限流自动换下一个）；候选 Claude、通义千问、DeepSeek 等 | F 负责对比 | 换模型只改 .env，由评测结果和成本决定 |

| 部署 | 前端 Vercel；后端用底座自带的 Dockerfile 上一台云服务器（也支持 Render） | D | 不再需要 Dify 账号 |

## 各模块实现方式

8 个模块里，第 2、3、4、7 个的 AI 部分是“提示词文件 + 后端函数”（E、F 写提示词，D 写函数）；第 1、5、6、8 个是普通业务逻辑，在后端写。标了“待实测”的地方要在前 2 天实际试过再定。

### 1. 资料上传与解析（直接方案，不用知识库）

1. 前端把文件交给后端；后端在 Supabase 存一份原件（以后接自建知识库时可以重新导入）。
2. **抽文字**：后端用 Python 库（如 PyMuPDF）按页抽出文字，存进“资料页”表（哪一讲、第几页、文字）。Word / PPT 先转成 PDF 再抽。前端用进度卡显示“读取中 / 好了 / 失败”。
3. **为什么不用 Dify 知识库**：它的解析和切块效果不理想（2026-11-03 定）。一讲课件一般几千到两三万字，主流模型一次装得下，两周内整讲交给模型更稳。
4. **留好替换口**：后端只通过一个“取资料内容”函数拿内容。现在它返回整讲全文（带页码）；以后接自建知识库时，改成返回检索到的片段，前端和 AI 能力不用改。
5. 图片、扫描件（P1）：走“图片转文字”工作流（多模态模型读图），结果当作一页文字存进资料页表。网页链接、录音两周内不做。
6. 限制：一次最多带 3 讲（具体字数以评测为准），超了就提示用 @ 选具体某讲。用文件哈希去重，重复上传不重新处理。
7. 用户隔离：资料页表按 user_id 存，用 Supabase 行级权限控制；前端永远拿不到模型的 API 密钥。

### 2. 学习文档生成（AI 能力）

- 做法：把资料文字交给模型，按固定 JSON 格式输出本节要点、知识点（名称 + 一句解释）、术语表、可能没弄懂的问题（提示词 F 写，函数 D 写）。
- 长资料由后端按章切开逐段调用，再调一次合并（F 写“逐段总结”和“合并”两份提示词）。
- 后端在资料索引完成后调用它，把 JSON 存进 notes 和 knowledge_points 表；用户改过的文档重新生成时不覆盖。

### 3. 资料问答（整讲全文 + AI 能力）

1. **问答链路**：后端先判断问的是哪一讲（用户 @ 了就用那一讲，否则用最近在学的一讲），用“取资料内容”拿到带页码的全文，和问题一起交给问答能力（E 的提示词 + D 的函数，经底座模型网关调用），不做检索。
2. **生成**：要求每句关键结论标出处【第 N 页】并摘一句原文；资料里没有的就说“你的资料里没提到，下面是通用知识”。
3. **核对出处**：后端检查摘的原句是否真的在那一页里，对不上就去掉这条出处，不让小满编造来源。
4. **引用展示**：前端显示讲次、页码和那句原文，点开在右侧工作台看那一页全文。
5. **流式返回**：后端用 SSE 把模型输出边生成边推给前端。底座的 /api/chat 是否已支持流式，第 1–2 天由 D 核实，不支持就加。
6. **费用**：整讲全文每次都要计 token，比检索贵。先看评测和账单；超预算就只带当前一讲，或改用便宜的备用模型。

### 4. 出题与判分（AI 能力）

- **出题**：输入知识点和这一讲全文（带页码） → 模型出题（JSON：题型、题干、选项、答案、解析、出处、难度）→ 再调一次“自检”，模型只看题干和原文作答，答案对不上的题丢掉 → 输出。
- **判分**：选择 / 判断 / 填空由后端直接比对；简答（两周先不做）以后调用“判分”能力，按评分要点打分并指出“你漏了哪一点”。
- 题目去重、作答记录（对错、用时、自评把握）、错题本都在后端。

### 5. 掌握度与复习调度（后端）

- 每个知识点一个掌握度（0–100），由最近的作答和自评更新。MVP 先用加权正确率，较新的作答权重更大。
- 复习时间用间隔重复算法：MVP 用 SM-2（简单），P1 换 FSRS（Anki 现在的算法，更准）；算法代码让 AI 写。
- 每天从“学新的（按目标拆解的进度）+ 练一练（学过的讲）+ 补一补（错题和到期的复习）”三处各取一件，再按当天强度定每件的分量，合并成“今天三件事”。

### 6. 计划与 agent（后端 + AI 能力）

- **计划**：把现有慢慢的计划逻辑（每天最多 3 件、顺延、断档回来、待安排区）移到后端，任务增加“类型 + 关联对象”：整理资料、做题、复习错题、上新课。
- **什么时候主动**：后端用规则判断——资料入库完成、一组题做完、每天首次打开、断档 ≥ 2 天、离考试剩 N 天。
- **说什么、建议做什么**：触发后调用“小满开场与建议”能力，它只能从固定动作里选（加任务、挪任务、出一组题、生成文档），输出 JSON 和一句小满的话；真正执行由后端做。
- **授权分级**：L0 只建议；L1 用户打开开关的小调整自动做；改期限、加减任务、换目标永远先问。
- **可撤销**：所有小满的动作写进动作日志（做前快照 + 做后快照），撤销 = 恢复做前快照。

### 7. 小满对话（底座的对话 + 我们的分流）

- 系统提示词 = 人设（像素卡皮巴拉、不制造愧疚）+ 后端传入的用户画像摘要（目标、考试日期、薄弱知识点、最近状态）。
- 对话记忆用底座自带的会话（LangGraph checkpoint）；底座的通用记忆卡两周内不在界面露出（学习记录就是记忆），怎么关由 D 第 1–2 天给方案。对话入口先过“理解用户想干嘛”：提问走问答、出题走出题、调安排出建议卡、闲聊交给底座原有对话。
- 用户问到资料内容时走模块 3 的问答链路；涉及改计划时不直接改，而是生成建议卡，走模块 6 的确认流程。

### 8. 数据看板（后端 + 前端）

- 所有行为写一张事件表（学习时长、上传、作答、完成任务、提问），看板用 SQL 聚合，每晚生成一份日汇总。
- 指标：学习天数与时长、各章节掌握度、正确率趋势、错题数变化、本周 vs 上周。
- 展示规则：只和自己的过去比；不显示断签和红色失败标记。

## 模型选型与评测

结论：每个 AI 能力配一套固定评测集，换模型、改提示词、改资料处理方式之前先跑一遍，分数不降才能合并。模型选择不凭感觉，看这张表的分数、延迟和每次调用成本。

### 评测集怎么来

- 先定 2–3 门样例课程（建议挑一门考证、一门技能课），收集真实资料：文字 PDF、扫描 PDF、PPT、手机拍的笔记各有几份。
- 6 个人每人标 20 条问答（问题 + 标准答案 + 答案在哪一页），合计约 120 条；其中故意放 20 条“资料里没有”的问题，测试会不会瞎编。
- 评测集进 Git，和代码一起版本管理；上线后把用户点踩的回答加进来。

### 每个能力评什么

| 能力 | 指标 | 建议达标线（待小组确认） | 怎么评 |
| --- | --- | --- | --- |
| 资料解析 | 文字提取准确率、页码对应正确率 | 文字版 ≥ 98%，扫描件 ≥ 90% | 抽样人工核对 |
| 出处 | 回答标的页码和原句真在资料里的比例 | ≥ 95% | 自动：后端核对原句是否出现在标的那一页 |
| 问答 | 答案正确率、引用正确率、无依据时诚实说明的比例 | 正确 ≥ 85%，引用 ≥ 90%，诚实 ≥ 90% | 模型评分（LLM-as-judge）+ 每轮人工抽 20 条 |
| 学习文档 | 要点覆盖率、有没有原文里没有的内容（幻觉） | 覆盖 ≥ 80%，幻觉 ≤ 2% | 对照人工列的要点清单 + 模型评分 |
| 出题 | 答案正确率、能在原文找到依据的比例、重复率 | 正确 ≥ 95%，重复 ≤ 5% | 人工抽 50 题 + 自动去重统计 |
| 简答判分 | 和人工打分的一致率 | ≥ 85% | 50 道人工打分的答卷对照 |
| 小满语气 | 不制造愧疚、不说教、一次只问一件事 | 违规 0 条 | 按规则清单模型评分 + 人工抽查 |
| 全链路 | 首字延迟、单次成本 | 问答首字 ≤ 3 秒 | Langfuse 统计 |

### 模型怎么选

1. 第 1–2 天在底座模型网关里接入两个候选模型（改 .env），先用其中一个把能力做起来；第 6–8 天用同一份评测集各跑一遍，定谁当主模型、谁当备用，并，出一张“分数 × 延迟 × 成本”对比表。换模型只改 .env 里的模型链。
2. 备用模型的用法：主模型出错、超时或额度用完时，底座模型网关自动切到备用模型（出错、超时、限流、空输出都会换下一个），演示不至于卡住。
3. 按任务分工使用：问答和出题用强模型；自检、摘要更新用便宜快的小模型。
4. 注意可用性：如果面向国内用户上线，海外模型可能访问不了或有合规问题，候选里必须有国内模型。

### 日常流程

- 评测脚本放在仓库 evals/：读评测集 → 批量调用本地后端的 AI 能力（先看底座 app/evals/ 和 tests/golden/ 能复用多少） → 让模型打分 → 生成网页报告。脚本让 AI 写，一条命令跑完。
- 改提示词、模型、一次带多少资料前后各跑一次评测（评测集 + 所有已修复的 bad case），分数不降才合并。
- 提示词按底座规矩存成 app/prompts/<名字>/vN.md，改一处就新建下一版，走 PR，PR 里贴评测分数前后对比。这样改动有记录，改坏了切回旧版本就行。
- 底座的调用轨迹和用量记录里能看到每次调用；回答下的 👍 / 👎（底座 /api/feedback）和后端自动检测到的错误都进 bad case 表，A 每天分诊，修好的加进评测集（见 PRD“Bad case 库与数据飞轮”）。

## 零基础怎么用 AI 完成分工

结论：大家不用先学会写代码，代码让 AI 写；每个人要会的是**把需求说清楚、看懂 AI 的方案、把程序跑起来检查对不对**。下面是所有人通用的做法，各角色的具体做法见后面一节。

### 用什么工具

| 工具 | 用来做什么 | 谁用 |
| --- | --- | --- |
| Claude Code / Codex | 读整个代码仓库、写前端代码、运行命令、修 bug、开 PR；两者任选其一，也可以互相复查对方写的代码 | 前端 B、C；产品 A 改原型 |
| VS Code + Claude Code 或 Codex 插件 | 在编辑器里写后端和脚本，选中代码直接问、直接改 | 后端 D；写评测脚本的 F |
| 底座仓库里的 app/prompts/ 和 evals/ | 写和改提示词文件、放评测用例、看评测报告 | E、F；其他人可以在本地跑起底座直接试 |
| Claude 对话（网页 / App） | 问概念、设计工作流和提示词、写文档、出评测题、看报错 | 所有人 |
| GitHub 网页 | 看任务看板、看 PR、留 review 意见 | 所有人 |
| 仓库根目录的 CLAUDE.md 和 AGENTS.md | 写清项目规矩（技术栈、目录、命名、“改代码前先说方案”）。Claude Code 读 CLAUDE.md，Codex 读 AGENTS.md，内容保持一致 | 产品 A 起草，全员维护 |

### 每个任务都走这 8 步

1. **从看板领一个 issue**：issue 里写着要做什么、怎么算做完（验收标准）。
2. **让 AI 先读、先说方案，不写代码**：把 issue 原文贴给 Claude Code 或 Codex，说“先读一下相关代码，用中文告诉我你打算怎么做、要改哪些文件，先别动手”。
3. **看懂方案再放行**：看不懂就追问“用不懂编程的人能听懂的话再讲一遍”；和接口文档对不上的地方，让它改方案。
4. **让 AI 开分支写代码**：“按这个方案实现，在新分支上做，做完告诉我怎么在本地跑起来看效果。”
5. **自己跑起来点一遍**：照着 AI 给的步骤启动，按验收标准逐条检查，截图留证。
6. **有问题就把现象原样告诉 AI**：报错信息整段复制、截图、说清“我点了什么、期望看到什么、实际看到什么”，让它修，回到第 5 步。
7. **让 AI 补测试并自查**：“给这次改动写自动测试并运行；再检查一遍有没有把 API key 写进代码、有没有改到别人负责的文件。”
8. **开 PR，请一位同学 + AI 一起 review**：让 AI 写 PR 说明（改了什么、怎么验证、截图）；同学在本地拉下来跑一遍再点通过，然后合并。

一个任务最好控制在 1–2 天内做完；AI 一次改太多文件时，让它拆成几个小 PR。

### 提示词任务的步骤（E、F 用）

和上面一样的思路，只是改的是提示词文件：

1. 领 issue，确认这个能力的输入、输出格式（和后端 D 对好）。
2. 让 Claude Code / Codex 先说方案：提示词分几部分、输出什么 JSON、新建哪个 app/prompts/<名字>/vN.md。
3. 本地用真实模型试 3–5 个样例；结果不对就把输入、输出贴给 AI，让它改提示词，一次只改一处、新建下一版。
4. 跑评测脚本（评测集 + 所有已修复的 bad case），分数不低于上一版才继续；底座的 pytest 和金标回归要全绿。
5. 开分支提 PR，请另一位 AI 同学拉下来跑一遍评测再合并。
6. 输入输出有变化时更新接口说明并通知 D。

### 和 AI 说话的 4 个习惯

- **给上下文**：说清是哪个页面、哪个接口、对应文档哪一节，直接贴 issue 和接口定义。
- **一次只做一件事**：“先做上传按钮”，而不是“把资料库整个做完”。
- **让它解释**：每次改完问一句“这次改了哪些文件、每个文件改了什么，用一句话说”。
- **卡住 30 分钟就求助**：先换个说法问 AI；还不行就在群里站会说“卡住了”，附上和 AI 的对话。

## 各角色的 AI 辅助做法

每个角色写了四件事：开工前花半天了解什么、AI 替你做什么、可以直接拿去用的提示词、怎么判断自己做对了。提示词里方括号的部分换成实际内容。

### A 产品 / 设计 / 项目管理

- **先了解**：GitHub 的 issue 和 Projects 看板怎么用；本文档的接口清单。
- **AI 替你做**：把本文档拆成 issue（每条带验收标准）、写 PRD 和小满语气规则、改 HTML 原型、起草仓库的 CLAUDE.md、每天把站会消息汇总成进度。
- **提示词**：“这是我们的技术方案（贴文档）。请按角色 B–F 拆成 GitHub issue，每条包含：标题、要做什么、验收标准（3 条以内，写成普通人能检查的操作）、依赖哪条 issue、预计天数（不超过 2 天，超过就拆）。”
- **做对了吗**：每条 issue 的验收标准，一个不懂技术的人点一点就能判断。

### B 前端 1（今天页、小满窗口、建议卡）

- **先了解**：用 Claude Code 或 Codex 把现有慢慢原型跑起来，在浏览器里点一遍；知道“页面”和“接口”的区别。
- **AI 替你做**：读懂现有代码、把本地假数据换成调用后端接口、写新组件、按截图调样式。
- **提示词**：“先用中文讲一下今天页的数据是从哪里来的，不要改代码。”→“把今天页的数据改成调用 GET /plan/today（接口定义贴这里）。后端还没好时先用 mock，结构和接口定义一致。做完告诉我怎么在浏览器里看效果。”
- **做对了吗**：照着原型图逐个按钮点；把浏览器窗口拉窄到手机宽度再看一遍；建议卡点“撤销”能恢复。

### C 前端 2（资料库、文档、练习、看板）

- **先了解**：同 B；再看一下 ECharts 官网的示例图，知道有哪些图可选。
- **AI 替你做**：按原型生成 5 个新页面、上传组件和进度条、做题交互、看板图表。
- **提示词**：“参考这张原型图（贴图），在现有项目里新加一个‘资料库’页。沿用项目已有的颜色和组件，不要新增依赖；数据先用 mock，字段按接口文档。”
- **做对了吗**：上传一个 PDF、一张图、一个超过 50 MB 的文件，三种情况界面都有正确提示；做题后错题本里能看到。

### D 后端（数据库、接口、部署）

- **先了解**：在 Supabase 网页上建一个项目，看懂“表、字段、一行数据”；知道 FastAPI 自带的 /docs 页面可以直接点接口测试；在 VS Code 里装好 Claude Code 或 Codex 插件；照 Personal-Agent 的 README 在本地跑起底座，读一遍它的 CONTRIBUTING.md。
- **AI 替你做**：按本文档的数据表生成建表脚本和行级权限、写接口、写 AI 能力函数（PDF 按页抽文字、取资料内容、经底座模型网关调各能力）、写 Docker 配置和部署步骤、写接口测试。
- **提示词**：“按这张表格（贴数据表一节）生成 Supabase 建表 SQL，每张表加 user_id 并开启行级权限，只允许本人读写。先给我看 SQL 并逐张表解释，确认后再执行。”
- **做对了吗**：用两个测试账号登录，A 看不到 B 的资料；/docs 页面里每个接口都能点通。

### E AI 1（问答与对话）

### 给零基础小组的技术简化

目的是少装、少部署、少出错：

- AI 能力不用拖拽平台，写成版本化提示词文件，由 AI 帮着写和改；两周内不用知识库，以后换成自己搭的知识库。
- 后端不从零写：以 Personal-Agent 为底座，模型网关、记账、反馈、回归测试、登录都现成。
- 两周内只放公开样例资料。
- 不上 Redis 任务队列：生成文档、出题用 FastAPI 自带的后台任务。
- 能在网页上点出来的就不写代码：数据库、文件存储在 Supabase 网页配；模型切换改 .env。

### 用 AI 的安全红线

- API key、数据库密码只放 .env 文件；不贴进对话、不写进代码、不提交到仓库、不出现在截图里。
- 不让 AI 直接改 main 分支，不合并自己没跑过的代码。
- AI 要执行删表、清空数据、强制推送一类命令时，先停下来在群里问。
- 内测用户的真实资料不拿来给 AI 当开发样例，开发只用 samples/ 里的公开资料。
- AI 说“已经完成”不算数，自己按验收标准点过一遍才算。

底座专属：模型密钥只在后端 .env，前端和截图里都不能出现；不动底座 CONTRIBUTING.md 第 3 节的安全规则，不删、不跳过它的测试；改提示词新建版本，不改旧版。

## 协作流程与里程碑

按 **2 周、共 10 个工作日** 排，分 4 段，中间有 3 道“关”，过关才进入下一段。整个节奏从演示倒推：第二天打开时小满能接上昨天的错题，这一刻必须真实跑通。最关键的是**第 5 天**：一份 PDF 从上传、生成学习文档、问答，一直走到做完 5 道题。它通了，后面是往上加功能；它不通，就先砍范围（见文末“风险”）。

### 协作规则

- **代码**：一个 GitHub 仓库，在 Personal-Agent 底座上开发（fork 到哪个账号待定）：后端用底座原有结构，前端放 web/，另加 evals/、docs/；main 分支受保护；每个功能开一个分支，PR 至少 1 人 review 才能合并。
- **任务**：用 GitHub Projects 看板，一个任务一个 issue，写清负责人、验收标准、预计天数；超过 3 天的任务要拆小。
- **节奏**：第 2、5、8 天下午各开一次关卡评审，现场演示，过关才往下走；每天在群里异步站会，三句话：昨天做了什么、今天做什么、卡在哪里。
- **接口变更**：先在群里说，更新 OpenAPI 文档，前端确认后再合并。
- **环境**：前端、后端各一条命令在本地启动；演示前手动部署一次到测试环境，两周内不做自动部署。
- **密钥与费用**：模型 API key 只放环境变量，不进仓库；每人一个 key 并设用量上限，每天看一次费用。
- **文档**：PRD、接口说明、评测报告、验收记录都放 docs/；继续维护交接文档。

## 风险与待定事项

### 风险

| 风险 | 影响 | 应对 |
| --- | --- | --- |
| 整讲全文太长：超出模型上下文，或费用太高 | 用户可能搜到别人的资料 | 前 2 天由 E 测一次最多能带几讲；超了只带当前一讲，或让用户用 @ 选讲 |
| 扫描件、手写笔记解析不准 | 后面问答和出题全部受影响 | MVP 先保证文字版 PDF；图片走读图工作流，入库前让用户预览 |
| 模型编造答案或出错题 | 学习产品最伤信任 | 强制引用、无依据诚实说明、出题自检，评测守门 |
| 模型费用不够，或底座本身有 bug（很新、只有一个作者） | 开发中途停摆 | 小任务用小模型；每天看用量；主模型额度不够时切到备用模型；用底座的每人费用上限；第 1–2 天先跑通底座全部测试，底座问题由 D 修 |
| 提示词被改坏没法回退 | 问答突然变差 | 提示词按版本存文件、走 PR；合并前跑评测 |
| 用户资料隐私与版权 | 资料泄露或被传播 | 两周内只放公开样例资料，不放真实用户资料；不做公开分享；可一键删除自己的全部数据 |
| 范围太大做不完 | 什么都半成品 | 按里程碑卡关；第 5 天没通就先砍图片和扫描件，学习文档只留要点和知识点 |
